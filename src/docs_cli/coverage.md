# LCOV summaries

`lcov_summary.py` calculates line and branch coverage for the code files
associated with each `primary_need_id`. It combines repeated LCOV records,
aggregates the selected files and rounds percentages to whole numbers. Equivalent
results produce identical JSON, allowing documentation builds to reuse their cache.

The responsibilities are split at the two files in the diagram below: Bazel
exports source ownership; the Docs CLI computes the summary; Sphinx displays it.
Plain LCOV is the workflow handoff. The summary JSON is a generated input local
to one documentation project, shared by the cache check and the renderer.

## Data flow and generated files

```text
(1) Bundle tree → Code-file lists ───┐
                                   ├→ (3) Coverage summaries → (4) Local documentation build
(2) LCOV report ────────────────────┘
```

1. **Code-file lists — one JSON file per `docs_bundle()`, generated by Bazel.**
   Each file maps `primary_need_id` to code files for the bundle itself and,
   recursively, its mounted child bundles. The generated Bazel target
   `:<bundle>.__internal__.code_file_lists` writes
   `<bundle>.__internal__.code_file_lists.json`.
   The root bundle created by `docs()` uses
   `:docs_bundle.__internal__.code_file_lists`.

2. **LCOV report — one optional input from the workspace.**
   The documentation workflow downloads `coverage-report-artifact` to
   `<workspace>/coverage-report/coverage_report.dat`. The Docs CLI reads this
   path when `bazel run` starts. If the report is absent, selected files have
   missing coverage.

3. **Coverage summaries — one JSON file per documentation project, generated by the CLI.**
   At startup, the CLI combines the root bundle's code-file lists from step 1
   with the LCOV report from step 2. It uses `lcov_summary.py` and writes
   `<build-output>/coverage_summary.json`. That file contains one summary per
   `primary_need_id` across the entire bundle tree. Its content determines whether
   the existing local documentation output can be reused.

4. **Local documentation build — receives the summary from step 3.**
   `bazel run :docs` and `:live_preview` prepare the summary before starting
   Sphinx. Cache cleanup preserves this generated input while removing stale
   documentation output.
   The `score_coverage` extension adds a compact display-only attribute in each
   matching Need's existing metadata area, using the normal attribute styling:
   `coverage: lines 67% · branches 100% · files 2/6`.
   `score_sphinx_bundle` loads this extension. Projects configuring extensions
   individually can enable `score_coverage` explicitly. The extension discovers
   `<build-output>/coverage_summary.json`; standalone Sphinx builds can override
   that path with `score_coverage_summary`. Without the extension, generated
   summaries have no effect on rendering.
   The report template extension uses the same summary through
   `score-coverage-report`, showing line and branch pies with percentage labels
   and measured/selected file counts. Missing and uninstrumented dimensions
   receive text instead of a pie. Percentages cover only the measured files;
   partial measurements are not presented as complete component coverage.
   Need IDs supply the association automatically. Missing measurements display
   as "no data"; uninstrumented dimensions display as "not instrumented".
   A content-only layout has no attribute area and receives no extra output.
   The Need's content and data fields remain unchanged.

`bazel build :needs_json`, `bazel run :docs_check` and `:docs_link_check` use
their existing inputs. Report parsing belongs to HTML rendering and live preview.

The generated file-list targets and JSON formats are internal interfaces. For a
concrete example, the [reference fixture](../tests/docs_bzl/scenarios/reference_integration/modern_module/BUILD)
provides:

```text
File-list target: //src/tests/docs_bzl/scenarios/reference_integration/modern_module:docs_bundle.__internal__.code_file_lists
File-list output: bazel-bin/src/tests/docs_bzl/scenarios/reference_integration/modern_module/docs_bundle.__internal__.code_file_lists.json
CLI target:       //src/tests/docs_bzl/scenarios/reference_integration/modern_module:docs
Summary output:   src/tests/docs_bzl/scenarios/reference_integration/modern_module/_build/coverage_summary.json
```

### Coverage report

The report belongs to the invoking workspace, including when docs-as-code is an
external module. Each CLI invocation reads its current content from
`coverage-report/coverage_report.dat`. An absent report is treated as empty LCOV.
Live preview reads coverage when its launcher starts; restart it after producing
a new report.

The input is plain LCOV text encoded as UTF-8. Archived coverage results are
extracted before the Docs CLI starts, so the file at the conventional path is
ready to read. Missing measurements are determined by comparing the LCOV records
with the selected files. Results use the measurements as supplied; the current
coverage-tool LCOV export excludes justification adjustments.

### Code-file lists

[`bzl/code_file_lists.bzl`](../../bzl/code_file_lists.bzl) exports repository-relative
file identities and their primary Need IDs from the composed bundle entries:

```json
{
  "version": 1,
  "code_file_lists": [
    {
      "primary_need_id": "mod__example",
      "bundle": "@@//docs:module",
      "files": [
        {"repository": "_main", "path": "src/example.cc"}
      ]
    }
  ]
}
```

Each bundle's `<name>.__internal__.files` target supplies the same bounded file
set used by source links. `<name>.__internal__.code_file_lists` serializes its
identities and accumulates the child bundles' lists. `bundle` identifies the
owner for diagnostics; aggregation uses `primary_need_id` and `files`.

The primary Need belongs to the bundle's own documentation, as checked by the
metamodel validation. Any Need type is supported. Bundles without a primary ID
are omitted; a primary ID with no selected files has `files.total: 0` and
`files.measured: 0`.
Conflicting primary IDs are errors. A file selected by multiple primary Needs
counts once for each; adding these summaries would double-count shared files.

### File identity

Files match by repository and repository-relative path. Bazel's `File.short_path`
supplies the exported identities. `_main` denotes the main repository; external
repositories retain their canonical Bazel names. In the exported JSON, `path`
is already scoped to its explicit `repository`; an `external/` directory inside
that path is an ordinary source directory.

The LCOV reader accepts repository-relative paths, leading `./`, external paths
in `external/<repo>/<path>` or `../<repo>/<path>` form, and generated paths with
a `bazel-out/<configuration>/bin/` prefix. Report and file lists must come from
the same workspace context. Absolute paths, parent traversal and virtual-include
aliases are rejected because they cannot be matched to the exported identities.

## Summary JSON, version 1

```json
{
  "version": 1,
  "coverage_summaries": [
    {
      "primary_need_id": "mod__example",
      "files": {"total": 3, "measured": 2},
      "lines": {"total": 10, "percent": 80},
      "branches": {"total": 0, "percent": null}
    }
  ]
}
```

`files.total` counts selected code files; `files.measured` counts those with
an LCOV record. Their difference is the number of files without measurements.
A total of zero means no files were selected. Partial summaries aggregate the
available records; the instrumented items in missing files are unknown.

Each dimension describes the available instrumentation:

| Measurement | `total` | `percent` |
| --- | --- | --- |
| No records available | `null` | `null` |
| Records present, no instrumented items | `0` | `null` |
| Instrumented items, none hit | Positive integer | `0` |
| Instrumented items with hits | Positive integer | Integer from 0 to 100 |

## Aggregation rules

Repeated records are combined by file, line number and branch identity
`(line, block, branch)`. Each instrumented item counts once; a hit in any record
covers it. A `BRDA` value of `-` represents an instrumented, unhit branch.
Items are aggregated across the selected files before rounding. Exact halves
round up: 12.5% becomes 13%.

`DA` and `BRDA` determine the metrics. Positive summary counters without matching
item records are rejected because their identities are needed for merging. Zero
summary counters without items describe an uninstrumented dimension. Branch
expressions may contain commas; block IDs must be numeric. Extended block flags
and location annotations are unsupported. Function records and unrelated LCOV
tags are ignored; malformed supported records are errors.

LLVM summary counters can count template instantiations differently from source
items; see [coverage_tool#8](https://github.com/eclipse-score/coverage_tool/issues/8).
For example, two hit `DA` entries with `LF:3`/`LH:2` produce 100% here, while the
summary counters give 67%. Combine reports from compatible instrumented builds:
branch numbers alone do not establish equivalent branches across backends.

## Cache behavior

The JSON contains instrumented totals, rounded percentages and file availability.
Its ordering and formatting are deterministic. Execution counters and exact hit
counts are used to calculate the rounded percentages. Changes that preserve
the summarized values preserve the output bytes and an existing file's
modification time. Changed results replace the file atomically; invalid input
leaves the existing output intact.

The Docs CLI calculates the summary before checking the local build cache and
adds the generated JSON to the existing sentinel files alongside the build
configuration. Equivalent summaries preserve the output directory and the
existing summary file. Changed summaries
invalidate the local output before Sphinx starts. This cache check runs on each
CLI invocation, so report changes are recognized even when Bazel's declared
code-file lists are unchanged.

## Running and checking

The Docs CLI imports `lcov_summary.py` as a library when these targets start:

```bash
bazel run //:docs
bazel run //:live_preview
```

Run the library and integration tests from the repository root:

```bash
bazel test //src/docs_cli:lcov_summary_test
.venv_docs/bin/python -m pytest -q src/tests/docs_bzl/test_coverage_summary.py
```

## Renderer example

The existing reference project contains normal Component Needs with code ownership.
Its checked-in `coverage.info` is a synthetic report for exercising this pipeline.
The integration test stages that report at the workspace input path, builds the
example and restores any previous report:

```bash
.venv_docs/bin/python -m pytest -q src/tests/docs_bzl/test_coverage_summary.py -k docs_use_summary
```

Inspect the generated page at
`src/tests/docs_bzl/scenarios/reference_integration/modern_module/_build/components/component/index.html`.
The test starts with 67% line coverage and 100% branch coverage, then changes the
report to 33% line coverage to check that the displayed result updates. The
baseline HTML is checked in at
`src/tests/docs_bzl/scenarios/reference_integration/modern_module/_expected/docs/components/component/index.html`.
The expected-output harness stages the scenario's `coverage.info` automatically.
The neighboring component has no summary and receives no coverage attribute.

## Reader and regression inputs

The required semantics are source-item identity, repeated-record merging and
branch coverage. `lcovparser.py` overwrites repeated filenames and rejects branch
records. The LCOV toolchain and coverage-tool's backend reporters provide broader
processing with additional runtime dependencies. This module uses a small Python
standard-library reader for the required records.

`fixtures/llvm.info` and `fixtures/gcov.info` are excerpts for `src/coverable.cpp`
from coverage-tool's hand-derived integration goldens:
`tests/end_to_end/expected/expected_lcov.dat` and `expected_lcov_gcov.dat`, at commit
`9ebc6bca8e0537b016a1de56891b5d96cf230e28`. They retain backend-specific item counts.
Synthetic records cover complementary hits, rounding, absent records, repository
identity and disagreement between item records and summary counters. Integration
tests cover bundle composition, artifact appearance/removal and documentation
cache reuse.
